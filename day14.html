01

WHY

AI 为什么会 "失忆"


AI 每次对话就像一场 "考试"，考完就清空记忆（上下文窗口是有限的）


AI 像一个每天失忆的实习生—— 每天来上班，什么都不记得，你要把公司情况每天讲一遍


讲一遍还好，项目越大、讲得越多，越容易讲漏、讲错

02

THE HANDBOOK

救星：CLAUDE.md或AGENTS.md

一个叫 CLAUDE.md 的文件，就是给 AI 的 "项目说明书",Codex里叫AGENTS.md


里面写什么（1/2/3 列清楚）：

1. 这是个什么项目（一句话介绍）

2. 技术栈是什么（Next.js/React/ 数据库…）

3. 哪些目录重要、常用命令是什么、开发时注意什么


AI 每次进项目自动读这个文件—— 不用你再交代


CLAUDE.md = 实习生的入职手册——AI 第一天上班先读手册，之后每天都知道自己该干嘛

03

SKILL & MCP

除了记忆，还要 "手艺" 和 "手眼"


光记住还不够 ——AI 要会干活还需要：


Skill = 岗位 SOP：怎么干这类活的步骤（比喻：厨师的拿手菜谱）


MCP = 工具权限：能打开网页、能查数据库（比喻：给实习生配了电脑和工牌）


一句话总结：CLAUDE.md 管 "记住"，Skill 管 "会做"，MCP 管 "能做"


三个比喻串起来：AI 实习生 = 入职手册 + 岗位 SOP + 办公权限

# 一、项目说明

这是一个基于 Next.js 的全栈 Web 项目。

主要技术栈：

- Next.js 15+

- React

- TypeScript

- Tailwind CSS

- shadcn/ui

- Supabase

- pnpm

包管理器统一使用：

```text

pnpm

```

不要擅自切换为 npm 或 yarn。

---

# 二、基本工作流程

处理开发任务时，遵循以下流程：

```text

理解需求

↓

检查现状

↓

制定方案

↓

修改代码

↓

验证结果

↓

汇报完成情况

```

## 1. 理解需求

首先理解用户真正需要解决的问题。

不要看到需求后立即修改代码。

如果需求存在明显歧义，并且不同理解会导致不同实现，应先向用户确认。

如果只是普通的技术细节，可以根据项目现有架构自行判断，不需要事事询问。

---

## 2. 检查现状

修改代码之前，应根据任务需要阅读：

- `AGENTS.md`

- `README.md`

- `package.json`

- 相关源代码

- 相关配置文件

- 已有组件

- 已有工具函数

- 已有类型定义

优先理解项目现有实现。

不要在没有检查现有代码的情况下重新实现一套类似功能。

---

## 3. 制定方案

对于复杂任务，修改前先确定：

- 需要修改哪些文件

- 是否需要新增文件

- 是否涉及 API

- 是否涉及数据库

- 是否涉及环境变量

- 是否影响现有功能

- 是否存在兼容性问题

简单修改可以直接实施，不需要为了流程而增加不必要的步骤。

---

# 三、项目目录规范

典型目录：

```text

src/

├── app/

│ ├── api/ # API 路由

│ └── ... # 页面与布局

│

├── components/

│ ├── ui/ # 基础 UI 组件

│ └── business/ # 业务组件

│

├── hooks/ # React Hooks

├── lib/ # 工具函数、服务、SDK

├── types/ # TypeScript 类型

└── config/ # 项目配置

```

新增文件时优先遵循项目已有目录结构。

不要因为个人偏好随意创建新的目录体系或架构层。

如果项目实际目录结构与本文件示例不同，以项目现有结构为准。

---

# 四、代码编写规范

## TypeScript

优先使用 TypeScript。

尽量避免：

```ts

any

```

优先定义明确的：

```ts

interface

type

```

代码应保持：

- 可读

- 简洁

- 职责清晰

- 类型明确

- 易于维护

不要为了炫技而使用不必要的复杂写法。

---

# 五、React 开发规范

统一使用函数组件。

默认优先使用服务端组件。

只有确实需要以下能力时，才使用：

```ts

"use client"

```

例如：

- `useState`

- `useEffect`

- 浏览器 API

- 客户端事件

- 客户端交互状态

不要为了方便而把整个页面或大范围组件全部改成客户端组件。

客户端组件的范围应尽可能小。

---

# 六、API 开发规范

第三方服务的私密 API Key 必须保存在服务端。

推荐调用方式：

```text

浏览器

↓

Next.js API 路由

↓

第三方 API

```

禁止：

```text

浏览器

↓

携带私密 API Key

↓

第三方 API

```

API 路由应该：

- 校验输入参数

- 正确处理异常

- 返回合理的 HTTP 状态码

- 返回结构化数据

- 避免泄露服务器内部信息

不要把以下内容直接返回给客户端：

- API Key

- 数据库密码

- 完整错误堆栈

- 服务器内部路径

- 私密 Token

- 数据库连接字符串

---

# 七、环境变量规范

私密环境变量，例如：

```env

OPENAI_API_KEY=

DATABASE_URL=

SUPABASE_SERVICE_ROLE_KEY=

```

只能在服务端使用。

只有明确允许公开的变量才能使用：

```env

NEXT_PUBLIC_*

```

本地环境变量通常放在：

```text

.env.local

```

不要把真实的 `.env.local` 提交到 Git。

如果项目需要提供环境变量示例，应使用：

```text

.env.example

```

例如：

```env

OPENAI_API_KEY=your_api_key_here

NEXT_PUBLIC_APP_URL=http://localhost:3000

```

禁止把真实密钥写入：

- 源代码

- README

- 测试代码

- Git 历史

- 日志

- 示例文件

---

# 八、安全规范

永远不要：

- 输出完整 Secret

- 提交 API Key

- 将密码写入源码

- 将 Service Role Key 暴露给浏览器

- 在日志中打印完整 Token

- 把私密环境变量放入 `NEXT_PUBLIC_*`

如果发现代码中存在疑似泄露的密钥：

1. 不要继续复制或传播该密钥。

2. 提醒用户存在安全风险。

3. 建议用户立即轮换相关密钥。

4. 根据用户要求协助清理代码或 Git 历史。

---

# 九、UI 开发规范

优先复用项目已有组件。

如果项目使用 shadcn/ui，应优先检查：

```text

src/components/ui/

```

是否已经存在可复用组件。

样式优先使用 Tailwind CSS。

除非用户明确要求，否则不要擅自引入新的：

- UI 框架

- CSS 框架

- CSS-in-JS 方案

- 组件库

新增页面或组件时，应尽量保持项目现有：

- 颜色

- 字体

- 间距

- 圆角

- 阴影

- 布局

- 交互方式

的一致性。

---

# 十、依赖管理

新增依赖之前，先检查：

1. 项目是否已经存在可以解决问题的依赖。

2. 是否可以使用现有工具函数解决。

3. 是否可以使用浏览器或 Node.js 原生能力解决。

4. 新增依赖是否真的必要。

安装正式依赖使用：

```bash

pnpm add <包名>

```

安装开发依赖使用：

```bash

pnpm add -D <包名>

```

不要使用：

```bash

npm install

yarn add

```

除非项目本身明确使用 npm 或 yarn。

---

# 十一、数据库规范

涉及数据库结构修改时：

- 优先使用 Migration

- 考虑已有数据兼容性

- 不要随意删除字段

- 不要随意删除表

- 不要随意修改已有字段含义

未经用户明确授权，不执行高风险数据库操作，例如：

```text

DROP TABLE

DROP DATABASE

TRUNCATE

```

如果操作可能导致数据丢失，应先说明风险。

---

# 十二、修改范围控制

遵循：

只做完成当前任务所必需的修改。

例如：

用户要求修复一个登录按钮，不要顺便重构整个认证系统。

除非用户明确要求，否则不要：

- 大规模重构

- 修改整体架构

- 更换框架

- 更换数据库

- 更换包管理器

- 批量升级依赖

- 修改无关代码

- 删除已有功能

- 批量格式化无关文件

如果发现其他问题，可以向用户说明，但不要擅自扩大任务范围。

---

# 十三、保护用户已有修改

假设当前工作区可能同时被以下对象修改：

- 用户

- 其他 AI Agent

- IDE

- 自动化脚本

- Git 工具

因此，不要因为某段代码不是自己生成的就擅自删除、覆盖或回滚。

如果发现与当前任务无关的已有修改，应尽量保留。

不要覆盖用户尚未提交的代码。

---

# 十四、代码验证

修改完成后，根据实际修改内容运行必要检查。

代码规范检查：

```bash

pnpm lint

```

TypeScript 类型检查：

```bash

npx tsc --noEmit

```

必要时运行完整构建：

```bash

pnpm build

```

如果项目存在自动化测试：

```bash

pnpm test

```

如果只修改 README、文档或注释，一般不需要运行完整构建。

验证范围应与修改范围匹配。

---

# 十五、禁止虚假汇报

不要声称：

```text

构建成功

测试通过

问题已经修复

页面运行正常

```

除非实际执行过相应验证。

例如，如果只运行了：

```bash

npx tsc --noEmit

```

只能说明：

```text

TypeScript 类型检查通过。

```

不能因此声称：

```text

项目构建成功。

```

如果因为环境、权限、网络等原因无法验证，应明确告诉用户。

---

# 十六、Git 安全规范

除非用户明确要求，否则不要自动：

- commit

- push

- merge

- rebase

- 创建 Pull Request

- 删除分支

- 修改 Git 历史

不要擅自执行高风险命令：

```bash

git reset --hard

git clean -fd

git push --force

```

涉及可能丢失代码的 Git 操作时，应先向用户说明风险。

---

# 十七、文档同步

如果修改导致以下内容发生变化：

- 环境变量

- 安装方式

- 启动方式

- API 使用方式

- 数据库配置

- 项目结构

- 部署方式

- 第三方服务配置

应根据需要同步更新相关文档。

不要让代码已经改变，但 README 仍然描述旧的使用方式。

---

# 十八、任务完成后的汇报

完成任务后，使用简洁的中文进行说明。

推荐格式：

```text

完成：

- 实现用户登录功能

- 增加登录状态检查

- 修复未登录用户访问问题

修改：

- src/app/login/page.tsx

- src/app/api/auth/route.ts

- src/lib/auth.ts

验证：

- pnpm lint ✓

- npx tsc --noEmit ✓

- pnpm build ✓

注意：

- 需要在 .env.local 中配置 SUPABASE_URL

- 数据库 Migration 尚未执行

```

只列出真正执行过的验证。

---

# 十九、自主决策原则

对于低风险、实现层面的普通技术问题，可以自行判断并继续工作。

例如：

- 变量命名

- 函数拆分

- 类型定义

- 小范围代码组织

- 明显 Bug 修复

对于以下情况，应优先向用户确认：

- 需求存在重大歧义

- 需要改变产品逻辑

- 需要修改核心架构

- 需要删除大量代码

- 可能导致数据丢失

- 需要执行不可逆操作

- 存在多个差异明显的产品方案

- 需要用户提供账号、密钥或外部配置

原则：

小事自主决定，大事先确认。

---

# 二十、核心原则

所有 AI Agent 应始终遵循以下原则：

1. 先理解，再修改。

2. 先检查现有实现，再创建新代码。

3. 能复用就不要重复实现。

4. 采用最小且正确的修改。

5. 不擅自扩大任务范围。

6. 保护用户已有代码和修改。

7. 永远不要泄露密钥。

8. 未经授权不要执行破坏性操作。

9. 验证之后再声称成功。

10. 重要风险和假设要明确告诉用户。

最重要的一条：

**只做完成当前任务所需要的最小且正确的修改。**
